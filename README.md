# Socket Programming

โปรเจกต์แอปแชตด้วย Python 3 และ TCP Socket หน้าหลักเป็นเว็บ HTML + Tailwind CSS + JavaScript เชื่อมผ่าน Python bridge (`aiohttp`) ไปยัง TCP Server เดิม

## สถานะปัจจุบัน: Part 2 ขั้นที่ 1–6

หน้าเว็บเชื่อมต่อ Server ด้วยชื่อไม่ซ้ำ และแสดงรายชื่อออนไลน์ที่อัปเดตตามการเข้า ออก และหลุด รวมชื่อตัวเองด้วย แต่ละแท็บมี WebSocket, `NetworkClient`, คิว และ TCP Socket แยกกัน

หน้าเว็บเลือกคนจากรายชื่อเพื่อเปิดห้องส่วนตัว ส่งข้อความ และแสดงข้อความของทั้งสองฝ่ายได้ แต่ละคู่มี `room_id` เดียวกัน แต่ละห้องมีแท็บ ช่องพิมพ์ ข้อความร่าง และตัวนับข้อความใหม่แยกกัน รับข้อความในห้องอื่นได้โดยไม่บังคับสลับแท็บ

ผู้ใช้ที่ลงชื่อแล้วสร้างกลุ่มได้หลายกลุ่ม ทุกคนเห็นชื่อ รหัสกลุ่ม และสมาชิก แม้ยังไม่ได้เข้ากลุ่ม ชื่อกลุ่มซ้ำได้โดยแยกด้วย `group_id` ตอนสร้างมีสมาชิกเพียงผู้สร้าง คนอื่นต้องกด Join ด้วยตัวเอง สมาชิกส่งข้อความและอ่านประวัติในแท็บกลุ่มได้ แต่คนเข้าใหม่ไม่เห็นข้อความก่อน Join ส่วน Leave จะเพิ่มในขั้นถัดไป

Server เก็บห้องและประวัติส่วนตัวใน `output/chat_state.json` และคืนแท็บห้องเดิมเมื่อลงชื่อกลับมา เมื่อเลือกแท็บจึงขอประวัติของห้องนั้น การปิด Client หรือ Server ไม่ลบประวัติ คู่สนทนาออฟไลน์ยังเปิดห้องเก่าอ่านได้ แต่ส่งข้อความใหม่ไม่ได้ ชื่อที่ว่างแล้วถือเป็นตัวตนเดิมตามนโยบายที่ตกลง ระบบนี้ยังไม่มีรหัสผ่าน

ข้อความกลุ่มเก็บใน `group_messages` ของไฟล์เดียวกัน พร้อม `visible_to` ซึ่งเป็นรายชื่อสมาชิกขณะส่ง รวมคนที่ออฟไลน์ Server ใช้ข้อมูลนี้กรองประวัติให้แต่ละคน โดยไม่ส่งฟิลด์สิทธิ์นี้ไปยัง Browser จึงส่งข้อความกลุ่มได้แม้คนอื่นออฟไลน์ และสมาชิกเดิมกลับมาอ่านย้อนหลังได้ ไฟล์ก่อน Step 6 โหลดต่อได้โดยไม่ลบกลุ่มหรือประวัติส่วนตัว

หน้าเว็บใช้โทนมืดตามภาพตัวอย่าง แถบรายชื่อและกลุ่มอยู่ด้านซ้าย พื้นที่ห้องอยู่ด้านขวา พร้อมฟอร์มเชื่อมต่อและสถานะ Offline, Connecting, Online หรือ Error ปรับการเรียงเมื่อหน้าจอเล็ก ใช้ Tailwind CLI สร้าง CSS ภายในโปรเจกต์ โดยไม่พึ่ง CDN ระหว่างเปิดแอป

โค้ด ชื่อตัวแปร และข้อความที่โปรแกรมแสดงเป็นภาษาอังกฤษ ส่วนคอมเมนต์และคำอธิบายเป็นภาษาไทย ข้อความแชตที่ผู้ใช้ส่งยังรองรับ UTF-8 รวมถึงภาษาไทย

## เปิดหน้าเว็บบนเครื่องเดียว

เตรียม dependency ครั้งแรก (ต้องมี Python 3 และ Node.js/npm):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm ci
npm run build:css
```

Terminal แรกเปิด TCP Server:

```bash
python3 server.py
```

Terminal ที่สองเปิด Python bridge:

```bash
.venv/bin/python web_bridge.py
```

เปิด [http://127.0.0.1:3000](http://127.0.0.1:3000) ใน Browser สองแท็บ:

1. ใช้ Server address `127.0.0.1` และ Port `5000` ทั้งสองแท็บ
2. แท็บแรกตั้งชื่อ `alice` แท็บที่สองตั้งชื่อ `bob` แล้วกด Connect แต่ละแท็บเห็นรายชื่อครบ รวมตัวเองที่มี `(you)`
3. ลองชื่อซ้ำ จะเห็น Error และแก้ชื่อเพื่อกด Connect ใหม่ได้
4. กด Disconnect หรือปิดแท็บหนึ่ง รายชื่ออีกแท็บเปลี่ยนตามจริง
5. หยุด TCP Server ด้วย `Ctrl+C` เว็บล้างรายชื่อ แสดงเหตุผล และให้เชื่อมต่อใหม่ได้เมื่อ Server กลับมา
6. หยุด bridge ด้วย `Ctrl+C` จะปิดการเชื่อมต่อของแท็บที่ bridge นั้นดูแล ส่วน TCP Server ยังทำงาน

พอร์ต `3000` คือ HTTP/WebSocket ภายในเครื่อง ส่วนช่อง Port `5000` บนหน้าเว็บคือพอร์ต TCP Server เป็นคนละหน้าที่ หากพอร์ตเว็บถูกใช้แล้ว ให้รัน `.venv/bin/python web_bridge.py --port 3001` แล้วเปิด URL ของพอร์ตใหม่

### ทดลองห้องส่วนตัว (Step 3)

1. ลงชื่อ `alice`, `bob`, `carol` ในสามแท็บ
2. ที่ Alice คลิก Bob ใน Online users จะเปิดแท็บ Bob พร้อมช่องพิมพ์และปุ่ม Send
3. พิมพ์ข้อความแล้วกด Send หรือ Enter; Shift+Enter ใช้ขึ้นบรรทัดใหม่ ข้อความตัวเองอยู่ขวา ของอีกฝ่ายอยู่ซ้าย
4. ที่ Bob จะได้แท็บ Alice โดยอัตโนมัติและตอบกลับได้ ข้อความขึ้นจากเหตุการณ์ของ Server เพียงครั้งเดียว ไม่เพิ่มซ้ำเมื่อได้รับ `sent`
5. ที่ Alice เปิด Carol แล้วลองสลับห้อง ข้อความและข้อความร่างไม่ปนกัน ถ้า Bob ส่งระหว่างอ่าน Carol แท็บ Bob จะแสดงจำนวนข้อความใหม่ โดยไม่เปลี่ยนห้องที่กำลังอ่าน
6. ปิดแท็บ Bob: ห้อง Bob ที่ Alice ยังอ่านประวัติได้ แต่ช่องส่งปิด เมื่อ Bob กลับมาใช้ชื่อเดิมจะส่งต่อในห้องเดิมได้
7. ปิดและเปิด TCP Server ใหม่ แล้วเชื่อมต่อชื่อเดิม เลือกแท็บห้องเก่าเพื่อโหลดประวัติและคุยต่อ
8. Carol ต้องไม่ได้ห้องหรือเนื้อหาของ Alice–Bob แม้ส่ง JSON ขอเปิดหรือส่งเข้า `room_id` ของคู่นั้นเอง

Server บันทึกข้อความก่อนกระจายแบบสด ถ้าบันทึกล้มเหลวจะไม่แสดงว่าเป็นข้อความสำเร็จ และหน้าเว็บเก็บข้อความที่ส่งไม่สำเร็จให้กด Use unsent text กลับมาใช้ได้ หากบันทึกแล้วแต่ผู้รับหลุดระหว่างส่ง จะแจ้งว่า saved แต่ live delivery ไม่สำเร็จ โดยประวัติยังอยู่ ถ้าการเชื่อมต่อของผู้ส่งขาดกลางทาง ให้เปิดห้องตรวจประวัติก่อนส่งซ้ำ ระบบไม่ resend อัตโนมัติ

ข้อมูลจริงอยู่ที่ `output/chat_state.json` ซึ่งถูก ignore ส่วนชุดทดสอบใช้ไฟล์ชั่วคราวคนละชุดเพื่อไม่ปนกับประวัติของผู้ใช้ สามารถกำหนด `CHAT_STATE_PATH` เพื่อเลือกไฟล์ประวัติอื่นได้ หากไฟล์เดิมเสีย Server จะแจ้งข้อผิดพลาดและไม่เขียนทับด้วยประวัติว่าง

### ทดลองสร้างและแสดงกลุ่ม (Step 4 — R8, R9)

1. ลงชื่อ `alice` กับ `bob` ในสองแท็บ ปุ่ม Create group จะเปิดใช้งานหลังลงชื่อสำเร็จ
2. ที่ Alice กด Create group กรอก Group name แล้วกด Create ฟอร์มจะปิดเมื่อ Server ยืนยันสำเร็จ ระหว่างรอจะกดสร้างซ้ำไม่ได้ หากผิดพลาดจะเก็บชื่อที่กรอกไว้ให้แก้
3. ทั้งสองแท็บเห็นกลุ่มเดียวกัน พร้อม `group_id` และ `Members: alice` โดย Alice เห็น You are a member ส่วน Bob เห็น Not joined
4. สร้างหลายกลุ่มหรือใช้ชื่อซ้ำได้ แต่รหัสแต่ละกลุ่มต้องต่างกัน จากนั้นเปิด Carol ทีหลังจะเห็นรายการปัจจุบันด้วย
5. ปิด Client ทุกคนแล้วเชื่อมต่อกลับ หรือหยุดและเปิด TCP Server ใหม่ กลุ่ม รหัส และสมาชิกเดิมยังอยู่ใน `output/chat_state.json` คนที่กลับมาใช้ชื่อเดิมยังเห็นว่าตัวเองเป็นสมาชิก
6. รายการแสดงเฉพาะ metadata ไม่ส่งเนื้อหาแชตไปด้วย การ Join อยู่ใน Step 5 และส่งข้อความกลุ่มใน Step 6 ส่วน Leave ยังไม่เปิดใช้

Server ใช้ชื่อจาก Socket ที่ลงทะเบียนเป็นผู้สร้าง ไม่รับรายชื่อสมาชิกจาก Browser บันทึกไฟล์ให้สำเร็จก่อนตอบ `group_created` ส่วนการ์ดทั้งหมดสร้างจาก `groups_updated` เท่านั้น จึงไม่เพิ่มซ้ำจากคำตอบรับ เลข `version` ป้องกันรายการเก่าทับรายการใหม่เมื่อหลายคนสร้างพร้อมกัน

### ทดลองเข้ากลุ่มด้วยตัวเอง (Step 5 — R10)

1. เปิด `alice`, `bob`, `carol` ในสามแท็บ ให้ Alice สร้าง Study group ตอนแรก Bob กับ Carol ต้องเห็น Not joined และปุ่ม Join โดยยังไม่มีแท็บกลุ่มนั้น
2. ให้ Bob กด Join ปุ่มจะแสดง Joining… และปิดชั่วคราว เมื่อ Server ยืนยันพร้อม snapshot สมาชิกแล้ว จึงเปิดแท็บกลุ่มของ Bob และเปลี่ยนปุ่มเป็น Open group
3. ทั้งสามคนต้องเห็นสมาชิกเป็น `alice, bob` แต่ Carol ยังไม่เป็นสมาชิกและยังไม่มีแท็บกลุ่ม
4. ให้ Alice กด Open group หรือเลือกแท็บ `# Study group` เพื่อดูสมาชิก การอัปเดตสมาชิกต้องไม่เปลี่ยนห้องที่กำลังอ่านหรือข้อความร่างของแชตส่วนตัว
5. ลองกลุ่มชื่อซ้ำ การ Join จะอ้างอิง group_id เฉพาะกลุ่มที่เลือก ไม่เพิ่มสมาชิกในอีกกลุ่ม และคำสั่ง Join ซ้ำไม่เพิ่มชื่อซ้ำหรือเลื่อน version
6. Bob Disconnect แล้วกลับชื่อเดิม หรือหยุดและเปิด Server ใหม่ สมาชิกยังอยู่ และแท็บกลุ่มกลับมาโดยไม่ต้อง Join อีก
7. สมาชิกเปิดแท็บกลุ่มและดูข้อมูลกลุ่มได้ ส่วนการส่งข้อความและประวัติอยู่ใน Step 6 แชตส่วนตัวยังใช้งานได้ตามเดิม

Server เชื่อชื่อจาก Socket เท่านั้น แม้ส่ง JSON แนบชื่อของคนอื่นมาก็เข้าร่วมแทนไม่ได้ การบันทึกสมาชิกใช้ Lock และแทนไฟล์แบบ atomic เช่นเดียวกับการสร้างกลุ่ม หากบันทึกล้มเหลวจะไม่ตอบว่าสำเร็จ และหน้าเว็บให้กด Join ลองใหม่ได้ การเปิดห้องกลุ่มใช้ Socket เดิม ไม่สร้าง Socket หรือ thread เพิ่มต่อกลุ่ม

### ทดลองข้อความและประวัติกลุ่ม (Step 6 — R5, R6, R11)

1. ให้ Alice สร้างกลุ่ม แล้ว Open group ส่งข้อความก่อน Bob เข้าร่วม จากนั้น Bob กด Join จะไม่เห็นข้อความก่อน Join
2. Alice กับ Bob ส่งตอบกลับด้วย Send หรือ Enter ได้ ใช้ Shift+Enter ขึ้นบรรทัดใหม่ ข้อความตัวเองอยู่ขวาและขึ้นจากเหตุการณ์ Server เพียงครั้งเดียว
3. Carol ที่ยังไม่ Join ต้องเห็นเพียงชื่อกลุ่มกับสมาชิก แม้ส่ง JSON ขอเปิดหรือส่งข้อความเข้ากลุ่มเอง Server ก็ปฏิเสธ
4. เมื่อ Carol Join จะเริ่มเห็นข้อความตั้งแต่นั้น ไม่โหลดประวัติก่อนหน้าให้ ส่วนสมาชิกเดิมยังเห็นประวัติที่ตัวเองมีสิทธิ์
5. ทดลองสองกลุ่มชื่อซ้ำและห้องส่วนตัว สลับแล้วข้อความร่างไม่ปนกัน ข้อความใหม่ของห้องอื่นมีตัวนับโดยไม่บังคับเปลี่ยนแท็บ
6. ให้ Carol Disconnect แล้ว Alice ส่งข้อความต่อ จากนั้น Carol กลับมาใช้ชื่อเดิมจะได้ประวัติช่วงออฟไลน์ที่ยังเป็นสมาชิก รวมหลังเปิด Server ใหม่
7. ถ้าคนอื่นออฟไลน์ทั้งหมด ยังส่งในกลุ่มได้ ต่างจากห้องส่วนตัวที่ต้องมีผู้รับออนไลน์

Server จัดลำดับต่อกลุ่มด้วย Lock และ `sequence` บันทึกข้อความก่อนส่งให้สมาชิกออนไลน์ หากผู้รับหนึ่งคนหลุดจะยังส่งให้คนอื่นต่อ พร้อมแจ้งผู้ส่งว่าบันทึกแล้วแต่ส่งสดไม่ครบ ไม่ส่งซ้ำอัตโนมัติ หากบันทึกไฟล์ไม่สำเร็จจะไม่เพิ่มข้อความสำเร็จ และมี Use unsent text ให้กู้ข้อความกลับช่องพิมพ์ เปิดห้องจะตรวจสมาชิกและคืนเฉพาะประวัติที่ชื่อนั้นอยู่ใน visible_to ลำดับแรกที่เห็นจึงอาจเริ่มที่เลขมากกว่า 1 ได้

เมื่อแก้ utility classes ใน `web/index.html` หรือ `web/app.js` ให้รัน `npm run build:css` ใหม่ หรือเปิด `npm run watch:css` ใน Terminal แยกเพื่อสร้าง CSS ทุกครั้งที่แก้ แล้ว refresh หน้าเว็บ Node.js ใช้ตอน build สไตล์เท่านั้น การรันแอปใช้ Browser และ Python

### แผนการเปิดข้ามเครื่อง

แต่ละเครื่อง Client รัน bridge ของตัวเองและเปิด `http://127.0.0.1:3000` ภายในเครื่อง จากนั้นกรอก IP จริงของเครื่อง TCP Server ในช่อง Server address ตัว bridge รับเฉพาะ loopback ส่วน TCP Server ต้องเปิดรับจากเครือข่ายตามแผน Part 1 (ปัจจุบัน `server.py` ยัง bind ที่ `127.0.0.1` สำหรับการทดสอบเครื่องเดียว)

```text
Browser A <-> local bridge A <-> TCP socket A <-> TCP Server
Browser B <-> local bridge B <-> TCP socket B <-> TCP Server
```

## Socket และ thread ต่างกันอย่างไร

**Socket คือช่องทางรับและส่งข้อมูล** ส่วน **thread คืองานที่แยกมาทำพร้อมกับงานอื่นภายในโปรแกรมเดียวกัน**

ฝั่ง Server มี Socket สองหน้าที่:

1. **Listening socket:** สร้างด้วย `socket()` แล้ว `bind()` และ `listen()` ไว้รอคนใหม่
2. **Connected socket:** `accept()` คืน Socket ใหม่สำหรับคุยกับ Client ที่เพิ่งเข้ามา แต่ละครั้งได้คนละ Socket

เมื่อมี alice และ bob จะมี listening socket หนึ่งตัว และ connected socket สองตัวบน Server ส่วน Client แต่ละโปรแกรมมี Socket ของตัวเองอีกหนึ่งตัว

```text
Server process
  Main thread: accept() waits for new clients
  Worker A: recv() reads from Alice's connected socket
  Worker B: recv() reads from Bob's connected socket

Local bridge process
  Event loop: Browser commands -> outgoing queue
  Sender thread A: outgoing queue -> Alice's TCP socket
  Receiver thread A: Alice's TCP socket -> events queue
  Event loop: events queue -> Browser
```

Thread A สามารถรอข้อมูลจาก alice โดยไม่ขวาง Thread B หรือการรับคนใหม่ ถ้า alice ส่งหา bob Thread A จะอ่านคำสั่งจาก Socket ของ alice แล้วเขียนข้อมูลไปที่ Socket ของ bob ขณะเดียวกัน Thread B ยังรออ่านข้อความที่ bob ส่งมาได้

Browser รับการคลิกและพิมพ์ ส่วน receiver thread ของ NetworkClient รอข้อมูลจาก Server จึงรับข้อความได้โดยไม่ต้องกดส่งก่อน การส่งและรับบน Socket เดียวกันทำได้พร้อมกัน แต่ให้มีตัวอ่านเพียงตัวเดียวต่อ Socket เพื่อไม่แย่งข้อมูลกัน

สำหรับ `NetworkClient` ที่ bridge ใช้ มี sender thread และ receiver thread แยกกัน เพื่อไม่ให้ `connect()` หรือ `sendall()` ขวางงานหน้าจอ เส้นทางเว็บคือ:

```text
Browser -> WebSocket -> bridge async handler -> outgoing queue -> sender thread -> TCP
TCP -> receiver thread -> events queue -> bridge async task -> WebSocket -> Browser DOM
```

งาน async ของ bridge แชร์ event loop เดียวกัน ไม่ได้เป็น Python thread ใหม่ต่อแท็บ แต่ละ session มี worker รับและส่งสอง thread ของตัวเอง และแต่ละ TCP Socket ใช้ส่งและรับได้พร้อมกัน เมื่อปิด session จะมีการรอ worker จบผ่าน executor เพื่อไม่ขวาง event loop ส่วน JavaScript ทำงานใน Browser คนละ process

Queue ไม่ได้สร้าง thread เพิ่ม bridge ตรวจคิวแบบไม่รอด้วย `get_nowait()` รอบละไม่เกิน 100 เหตุการณ์ แล้วคืนเวลาให้ event loop ประมาณ 20 มิลลิวินาที

Server ส่ง `users_updated` พร้อม `version` ที่เพิ่มเมื่อคนเข้าออก ทั้งฝั่งส่งและฝั่งรับป้องกันการใช้รายการเก่าย้อนทับรายการใหม่ ส่วน `registered` ต้องมาก่อนรายชื่อหรือข้อความอื่นบนการเชื่อมต่อนั้นเสมอ รายละเอียดอยู่ใน `docs/protocol.md`

## รายชื่อและ Lock

Server ใช้ dictionary กลาง แนวคิดเป็น:

```python
clients = {
    "alice": alice_connection,
    "bob": bob_connection,
}
```

ค่าของ dictionary ในโค้ดจริงเป็น `ClientConnection` ซึ่งรวม Socket ชื่อที่ลงทะเบียน และกุญแจการส่งของคนนั้นไว้ด้วยกัน

| กุญแจ | ป้องกันอะไร |
| --- | --- |
| `clients_lock` | การตรวจชื่อซ้ำ เพิ่ม ลบ และค้นหาการเชื่อมต่อพร้อมกัน |
| `client.send_lock` | หลาย thread ส่งเข้า Socket ของผู้รับเดียวกันจนข้อมูล JSON แทรกกัน |

`Lock` เปรียบเหมือนกุญแจที่ให้เข้าทำงานส่วนหนึ่งได้ทีละงาน ใช้ `with lock:` เพื่อให้ปล่อยกุญแจเมื่อทำเสร็จหรือเกิดข้อผิดพลาด เราปล่อย `clients_lock` ก่อนส่งข้อมูลผ่านเครือข่าย เพื่อไม่ให้ผู้รับที่ช้าขวางการจัดการรายชื่อทั้งหมด

ตอนลงชื่อ Server ล็อกฝั่งส่งก่อนเพิ่มชื่อเข้ารายการ เพื่อให้คำตอบ `registered` มาก่อนข้อความจากคนอื่นที่อาจส่งมาทันที และตอนลบชื่อจะตรวจว่าเป็นการเชื่อมต่อเดิม เพื่อไม่เผลอลบคนใหม่ที่กลับมาใช้ชื่อเดียวกัน

## ข้อความ JSON และ flow

Client ลงทะเบียนชื่อ:

```json
{"type": "register", "name": "alice"}
```

Server ตอบรับ:

```json
{"type": "registered", "name": "alice"}
```

alice ส่งหา bob:

```json
{"type": "message", "to": "bob", "text": "Hello Bob!"}
```

Server ใช้ชื่อที่ผูกกับ Socket ของผู้ส่งเติม `from` เอง แล้วส่งเฉพาะให้ bob:

```json
{"type": "message", "from": "alice", "to": "bob", "text": "Hello Bob!"}
```

Server แจ้งสถานะกลับให้ alice:

```json
{"type": "sent", "to": "bob"}
```

การแจ้งชื่อยังไม่ใช่ระบบยืนยันตัวตนด้วยรหัสผ่าน ส่วนคำสั่งหรือข้อมูลผิดจะตอบด้วย `error` หาก JSON เสียหรือการเชื่อมต่อจบกลางบรรทัด จะพยายามแจ้งข้อผิดพลาดแล้วปิดเฉพาะ Client คนนั้น

```text
Client -> register -> Server -> registered -> Client
Alice -> message(to=bob) -> Server -> message(from=alice) -> Bob
                                  -> sent -> Alice
Browser -> disconnect -> bridge closes TCP socket -> Server removes that connection
Server continues accepting other clients
```

## กติกาข้อความจากขั้นที่ 3 ที่ยังใช้ต่อ

- `send_message()` ใช้ `json.dumps()` → เติม `\n` → เข้ารหัส UTF-8 → `sendall()`
- `receive_messages()` ใช้ `recv()` → เก็บ buffer → แยกบรรทัด → ถอดรหัส UTF-8 → `json.loads()`
- JSON หนึ่งข้อความต่อหนึ่งบรรทัดช่วยแยกข้อมูลเมื่อ TCP แบ่งข้อความมาหลายส่วน หรือรวมหลายข้อความมาในครั้งเดียว
- ขึ้นบรรทัดใหม่ภายในข้อความจะถูก JSON escape จึงไม่สับสนกับตัวจบข้อความ
- `yield` คืนข้อความทีละรายการและจำ buffer ไว้ receiver thread ใช้ generator เดียวตลอดการเชื่อมต่อ
- `threading.Event` ใช้แจ้งให้งานรับและงานหลักรู้ว่าต้องหยุด และ `shutdown(SHUT_RDWR)` ปลุกงานที่กำลังรอ Socket ก่อนปิดโปรแกรม

## การทดสอบ

```bash
.venv/bin/python -B -m unittest discover -s tests -v
```

ทดสอบการแบ่งและรวมข้อความ UTF-8 ชื่อซ้ำ การส่งส่วนตัว การส่งพร้อมกัน การนำชื่อกลับมาใช้ และการปิด Server รวมถึง WebSocket bridge หลาย session และการปิดแท็บ/bridge โดยใช้พอร์ตว่างอัตโนมัติสำหรับการทดสอบ ไม่รบกวน Server ที่พอร์ต `5000` หากไม่ได้ติดตั้ง aiohttp ชุดทดสอบ bridge จะข้ามตัวเอง

ชุดทดสอบปัจจุบันใช้ protocol, TCP Server, NetworkClient และ WebSocket bridge จึงไม่ต้องติดตั้ง Tkinter หรือใช้ Xvfb

การทดสอบต้องเปิด Socket ภายในเครื่อง หากรันผ่านเครื่องมือที่จำกัดสิทธิ์เปิด Socket อาจต้องอนุญาตการทดสอบก่อน

ผลตรวจปัจจุบัน: ผ่านการทดสอบ 74 กรณี ครอบคลุม protocol รายชื่อออนไลน์ ห้องส่วนตัว สิทธิ์ ประวัติ กลุ่ม การสร้าง/เข้าพร้อมกัน การปฏิเสธ Join ก่อนลงชื่อหรือรหัสกลุ่มผิด การไม่รับชื่อคนอื่นมา Join แทน การ Join ซ้ำ การบันทึกล้มเหลว สมาชิกเดิมเมื่อเชื่อมต่อกลับหรือเปิด Server ใหม่ และการปิด Server/bridge โดยไม่ต้องมี display รวมข้อความกลุ่ม การกรองประวัติก่อน Join ผู้รับหลุดแล้วคนอื่นยังได้รับ ลำดับข้อความจากผู้ส่งพร้อมกัน และการโหลดไฟล์ก่อน Step 6 โดยไม่รีเซ็ตข้อมูล

ผลตรวจ Browser ใน Step 4: ทดลองสามแท็บ ตรวจฟอร์ม Create/Cancel และข้อผิดพลาด ชื่อกลุ่มซ้ำ ภาษาไทย ผู้ใช้เข้าทีหลัง การเชื่อมต่อกลับ สมาชิก/Not joined และสร้างจากหน้าจอมือถือแล้ว แชตส่วนตัวยังส่งถึงคู่สนทนาโดย Carol ไม่ได้รับข้อความ ตรวจขนาด 1280 × 900 และ 390 × 844 ไม่มีหน้าล้นแนวนอน และ build Tailwind/ตรวจ syntax JavaScript ผ่าน

ผลตรวจ Browser ใน Step 5: Bob กด Join แล้วได้แท็บกลุ่ม ทุกคนเห็นสมาชิกเป็น Alice กับ Bob โดย Carol ยังไม่ถูกเพิ่ม จากนั้น Carol Join จากขนาด 390 × 844 ได้ ขณะที่แท็บส่วนตัวและข้อความร่างของ Bob ยังอยู่ครบ แชตส่วนตัวยังส่งได้โดย Carol ไม่ได้รับข้อความ และเมื่อ restart Server กลุ่ม สมาชิก และแท็บเดิมกลับมาจากไฟล์โดยไม่ต้อง Join ซ้ำ ตรวจขนาด 1280 × 900 และหน้าต่างสูง 720 พิกเซลด้วย โดยเนื้อหากลุ่มเลื่อนอ่านได้ ไม่มีหน้าล้นแนวนอนหรือ Browser error

ผลตรวจ Browser ใน Step 6: ส่งตอบกลับและข้อความไทยหลายบรรทัดในกลุ่มผ่าน Send/Enter ได้ Bob ไม่เห็นข้อความก่อน Join และ Carol ที่ยังไม่ Join ไม่ได้รับเนื้อหากลุ่มหรือส่วนตัว สองกลุ่มชื่อซ้ำแยกด้วยรหัสและเก็บข้อความร่างแยกกัน ข้อความใหม่ไม่บังคับสลับห้องและมีตัวนับ Carol ส่งจากขนาด 390 × 844 ได้ จากนั้นเปิด Server ใหม่แล้วเห็นเฉพาะประวัติที่มีสิทธิ์ รวมข้อความช่วงออฟไลน์ และส่งต่อได้ขณะออนไลน์คนเดียว ตรวจขนาด 1280 × 900 และมือถือ ไม่มีหน้าล้นแนวนอนหรือ Browser error ข้อความขึ้นครั้งเดียวหลังรับคำตอบและโหลดประวัติกลับมา
