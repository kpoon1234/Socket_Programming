# Part 3: Special Features

โฟลเดอร์นี้ใช้รวมโมดูลของฟีเจอร์ Part 3 โดยแยกหนึ่งโฟลเดอร์ต่อหนึ่งฟีเจอร์ แผนหลักอยู่ใน [flow/part3.md](../flow/part3.md)

## Requirement จากโจทย์

- Part 3 มี 4 คะแนน ฟีเจอร์ละ 1 คะแนน
- ต้องมีฟีเจอร์ AI อย่างน้อยหนึ่งฟีเจอร์ โดย text summarization เป็นหนึ่งในตัวอย่างที่โจทย์ระบุ
- Part 2 ต้องครบก่อน Part 3 จึงจะถูกตรวจให้คะแนน และยังต้องเตรียมสไลด์ Implementation Explanation กับเดโม
- คะแนนขึ้นกับการทำงานและการตรวจจริง การตั้งชื่อโมดูลหรือเพิ่มหลายปุ่มไม่ได้แปลว่าเป็นหลายฟีเจอร์โดยอัตโนมัติ

อ้างอิง: Computer_Network_Term_Project___Socket_Programming.pdf หน้า 2

## รายการฟีเจอร์

| ลำดับ | ฟีเจอร์ | สถานะ |
| --- | --- | --- |
| 1 | AI text summarization ผ่าน Groq | ต่อ Server/Socket/หน้าเว็บแล้ว ใช้ได้ทั้งห้องส่วนตัวและกลุ่ม |
| 2 | End-to-End Encryption (E2EE) | เข้ารหัส ChaCha20 + SHA-256 ด้วย Passcode PIN |
| 3 | Unsend Message (ยกเลิกข้อความ) | ยกเลิกข้อความทั้งแชตส่วนตัวและกลุ่ม ซิงก์สดและบันทึกลงประวัติ |
| 4 | ยังไม่เลือก | รอตกลง |

## การจัดไฟล์

ไฟล์ของฟีเจอร์สรุปและฟีเจอร์อื่น ๆ:

```text
feature/
  README.md
  summarize/
    __init__.py
    README.md
    ai_summarize.py
    service.py
  E2EE/
    e2ee.js
  unsent/
    README.md
  <next_feature>/
```

- `summarize/ai_summarize.py`: อ่าน `.env` และ environment เรียก Groq ด้วย timeout 30 วินาที ปิด retry อัตโนมัติ และคืน `SummaryError` ที่มี `code` กับข้อความปลอดภัยสำหรับผู้ขอ โดยไม่แสดง key หรือ response body อ้างอิงการใช้ SDK จาก [Groq Python](https://github.com/groq/groq-python)
- `summarize/service.py`: รับ snapshot ที่ Server ตรวจสิทธิ์แล้ว เรียงจากเก่าไปใหม่ เลือกข้อความล่าสุดไม่เกิน 30 ข้อความและเตรียมคำสั่งสรุปภาษาไทย
- [summarize/README.md](summarize/README.md): อธิบายแต่ละฟังก์ชันในโมดูลสรุปและส่วนที่เพิ่มใน Server
- ฟีเจอร์ถัดไปเพิ่มในโฟลเดอร์ใหม่ภายใต้ `feature/` เมื่อตกลงว่าจะทำอะไร
- จุดเชื่อมกับแอปอยู่ใน `server.py`, `web_bridge.py`, `web/app.js` และ `web/index.html` ตามหน้าที่เดิม เพราะ Part 3 ต่ออยู่ในแอปเดียวกัน
- เก็บการทดสอบใน `tests/` และข้อมูลที่โปรแกรมสร้างใน `output/` เดิม ไม่เก็บ API key หรือประวัติจริงในโฟลเดอร์ source code

## เตรียมค่าตั้ง Groq

คัดลอกไฟล์ [.env.example](../.env.example) เป็น `.env` ที่ root ของโปรเจกต์:

```bash
cp .env.example .env
```

แก้ `GROQ_API_KEY` เป็น key ของตัวเอง และ `GROQ_MODEL` เป็น model ID ที่บัญชีเรียกใช้ได้ เก็บค่าจริงเฉพาะเครื่อง Server โดย `.gitignore` ละเว้น `.env` อยู่แล้ว

## สถานะการพัฒนา

ทดลองเรียก Groq API จริงด้วย `openai/gpt-oss-20b` สำเร็จเมื่อ 2026-11-05 และได้สรุปภาษาไทยจากบทสนทนาจำลองแล้ว ลบสคริปต์ทดลองหลังใช้งานเสร็จ และเตรียมแพ็กเกจ `feature/summarize/` ไว้สำหรับโค้ดฟีเจอร์จริง

เขียน `ai_summarize.py` และ `service.py` แล้ว โมดูล AI อ่าน `.env` ที่ root ของโปรเจกต์เมื่อถูกเรียก โดย environment มีสิทธิ์เหนือไฟล์ และไม่เปลี่ยน environment ของโปรแกรม ใช้ `openai/gpt-oss-20b` เมื่อ `GROQ_MODEL` ว่างหรือยังเป็น placeholder

### การเลือกข้อความและผลลัพธ์

- รับเฉพาะ snapshot ที่ Server ตรวจสิทธิ์แล้ว ไม่อ่านประวัติเองและไม่รับข้อมูลจาก Browser โดยตรง
- ใช้ไม่เกิน 30 ข้อความล่าสุด โดยมีเพดาน JSON input 6,000 UTF-8 bytes รวมชื่อผู้ส่ง เวลา และรูปแบบ JSON เพดานนี้ไม่ใช่จำนวน token ที่แน่นอน และไม่รวม system prompt/ผลลัพธ์
- หากเกินขนาดจะลดข้อความเก่าจากช่วงท้าย โดยเก็บแต่ละข้อความครบและไม่ข้ามช่วง ถ้าข้อความล่าสุดรายการเดียวเกินเพดานจะคืน `input_too_large` ให้ผู้ขอ
- ไม่เรียก API เมื่อไม่มีข้อความที่ไม่ว่าง ส่งให้ AI เฉพาะ `from`, `text` และ `timestamp` ไม่ส่ง `visible_to` หรือ metadata ภายใน
- แยก system prompt ออกจากบทสนทนาที่เข้ารหัส JSON และไม่เปิด tools ให้โมเดล การแยกนี้ช่วยลดความเสี่ยงจากคำสั่งในแชต แต่ยังต้องตรวจสิทธิ์ที่ Server เสมอ
- ผลสรุปภาษาไทยแยกเป็นประเด็นสำคัญ ข้อตกลง และงานที่ต้องทำ หากไม่มีข้อมูลให้บอกว่าไม่มีข้อมูล

เรียก `summarize_messages(authorized_messages)` จาก `feature.summarize.service` แล้วจะได้ dictionary ที่มี `summary`, `message_count`, `first_message_id`, `last_message_id`, `input_bytes` และ `truncated` เพื่อแสดงจำนวนและช่วงข้อความจริงที่ใช้

Server ตรวจสิทธิ์และอ่าน snapshot แล้วปล่อย state/room lock ก่อนเรียกโมดูลนี้ใน worker จำกัด 2 งานพร้อมกันทั้ง Server และ 1 งานต่อการเชื่อมต่อ ไม่มีคิวรอไม่จำกัด หากเต็มตอบ `summary_busy` ตรวจสิทธิ์และ session ซ้ำก่อนคืนผลให้ผู้ขอ เมื่อ Leave กลุ่มจะยกเลิกผลคำขอก่อนออกแม้ Join กลับระหว่างรอ

หน้าเว็บมีปุ่ม Summarize ทั้งห้องส่วนตัวและกลุ่มแบบปกติ โดย Secret Chat ซ่อนปุ่ม คำอธิบาย และผลสรุป และ Server ปฏิเสธคำขอด้วย `secret_chat_unsupported` ก่อนเรียก AI แสดงสถานะกำลังสรุป จำนวนและช่วงข้อความ และข้อผิดพลาดในพื้นที่ AI summary โดยใช้ `textContent` ผลแยกตามห้อง ไม่บันทึกลงประวัติ ไม่ส่งให้สมาชิกอื่น และถูกล้างเมื่อออกจากการเชื่อมต่อ/ออกกลุ่ม สลับแท็บระหว่างรอได้โดยผลไม่บังคับเปิดห้องเดิม การแชตยังทำงานต่อได้ และห้องส่วนตัวยังสรุปประวัติได้เมื่อคู่สนทนาออฟไลน์

กล่องสรุปเรียงอยู่หลังข้อความสุดท้ายในช่วงที่สรุป ข้อความใหม่จึงต่อด้านล่างและดันสรุปขึ้นตามลำดับการสนทนา แต่ละห้องเก็บเพียงผลล่าสุดในหน่วยความจำหน้าเว็บ กดใหม่จะแทนที่ผลเดิมและย้ายกล่องไปยังช่วงใหม่ การรีโหลดหน้าเว็บทำให้ผลหาย ส่วนข้อความแชตต้นฉบับยังบันทึกใน `output/chat_state.json` ตามระบบเดิม

### การทดสอบ

```bash
.venv/bin/python -m unittest discover -s tests -p test_summarize.py -v
.venv/bin/python -m unittest discover -s tests -p 'test_summary*.py' -v
```

ผ่าน 13 รายการ ครอบคลุมจำนวน/ลำดับข้อความ ขนาด UTF-8 และ JSON การรับ snapshot ที่กรองช่วงก่อน Join/ช่วง Leave แล้ว การตั้งค่า และข้อผิดพลาดของผู้ให้บริการ ชุดทดสอบใช้ตัวแทน API จึงไม่ใช้ key จริงหรือโควตา

เพิ่มการทดสอบผ่าน TCP และ WebSocket อีก 11 รายการ ตรวจสิทธิ์ส่วนตัว/กลุ่ม การ Leave/Join ระหว่างรอ การหลุดแล้วใช้ชื่อเดิม การจำกัดงานพร้อมกัน การส่งแชตระหว่างรอ และการส่งผลเฉพาะผู้ขอ ชุดทดสอบทั้งหมดของโปรเจกต์ผ่าน 109 รายการ รวมทั้งตรวจ JavaScript และ build CSS แล้ว

ทดลองหน้าเว็บกับ Groq จริงโดยใช้บทสนทนาจำลองในประวัติชั่วคราวสำเร็จ ผลสรุปกลับมาที่ห้องต้นทางหลังสลับแท็บ การทดลองนี้ยืนยันเส้นทาง API จริง ส่วนคุณภาพการสรุปยังต้องประเมินกับบทสนทนาหลายแบบ เพราะโมเดลอาจตกหล่นรายละเอียดได้
