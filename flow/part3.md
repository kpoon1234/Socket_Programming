- ต้องทำ Part 2 ให้ครบก่อนตรวจ Part 3 และเตรียมสไลด์อธิบายพร้อมเดโม
- Text summarization เป็นฟีเจอร์แรก ส่วนฟีเจอร์ที่เหลือยังไม่เลือก

## 2. ฟีเจอร์แรก: AI Text Summarization

แนวคิด: ผู้ใช้เปิดห้องส่วนตัวหรือห้องกลุ่ม กด Summarize แล้วอ่านสรุปบทสนทนาโดยไม่ต้องไล่อ่านทุกข้อความ

ข้อเสนอเริ่มต้นที่ต้องตกลงก่อนเขียน:

- ใช้ปุ่ม Summarize ในห้องปัจจุบัน ผู้ใช้เป็นผู้กดเรียกเอง
- เริ่มด้วยข้อความล่าสุดไม่เกิน 30 ข้อความที่ผู้กดมีสิทธิ์อ่าน พร้อมเพดานขนาด input/token ไม่ใช้จำนวนข้อความอย่างเดียวตัดสินว่ารับได้ ระบุช่วงและจำนวนข้อความที่สรุปให้ชัดเจน
- ใช้ได้ทั้งห้องส่วนตัวและห้องกลุ่ม โดยทดสอบเส้นทางให้จบทีละชนิดห้อง
- สรุปภาษาไทยเป็นหัวข้อสั้น ๆ: ประเด็นสำคัญ ข้อตกลง และงานที่ต้องทำ ถ้าไม่มีข้อมูลให้บอกว่าไม่มี ไม่เดาขึ้นเอง
- แสดงผลในพื้นที่ AI summary แยกจากข้อความแชต ให้เฉพาะผู้กดเห็น ไม่ส่งเป็นข้อความใหม่ให้ทั้งห้อง
- รุ่นแรกเก็บผลเฉพาะใน session ของผู้ขอ ไม่บันทึกลงประวัติแชตหรือแชร์ต่ออัตโนมัติ
- ชื่อปุ่มและ UI เป็นภาษาอังกฤษ ส่วนเนื้อหาสรุปเป็นภาษาไทยตามตัวเลือกที่ตกลง

## 3. เหตุผลที่เสนอ Groq

- เรียกใช้งานผ่าน Python SDK ได้ จึงต่อกับ Server Python เดิมโดยไม่ต้องฝึกหรือรันโมเดลบนเครื่องเอง
- Groq เป็นบริการที่รันโมเดลให้เรา ส่วนชื่อโมเดลเป็นอีกค่าหนึ่ง เช่น `openai/gpt-oss-20b` ซึ่งอยู่ในรายการ production models ณ วันที่ตรวจเอกสาร 2026-11-05 ชื่อนี้เป็นตัวเลือกสำหรับทดลอง ไม่ใช่ค่าที่ล็อกไว้แล้ว
- ทดสอบคุณภาพภาษาไทยกับบทสนทนาจำลองก่อนเลือกโมเดล และเก็บชื่อโมเดลใน `GROQ_MODEL` เพื่อเปลี่ยนได้
- มีข้อจำกัดตามโมเดลและบัญชี ต้องเช็ก Limits ในบัญชีจริงก่อนเดโม เมื่อเกินโควตา API อาจตอบ 429
- การใช้บริการนี้ต้องมีอินเทอร์เน็ตและส่งข้อความที่เลือกไปยัง Groq ควรแสดงข้อมูลนี้ใกล้ปุ่มสรุป

แหล่งข้อมูลทางการที่ตรวจเมื่อ 2026-11-05:

## 4. เส้นทางข้อมูลที่เสนอ

```text
Browser: click Summarize
  -> WebSocket -> local Python bridge -> NetworkClient -> TCP Server
  -> verify room access and read an authorized message snapshot
  -> Part 3 summary service -> Groq API over HTTPS
  -> TCP -> NetworkClient -> local bridge -> WebSocket
  -> AI summary panel in the requesting browser tab
```

- ข้อความแชตและคำขอสรุประหว่าง Client กับ Server ยังคงใช้ TCP Socket เดิม ส่วน HTTPS เป็นการเรียกบริการ AI จาก Server
- เก็บ API key เฉพาะเครื่อง Server ไม่ส่งให้ Browser และไม่ต้องให้ Client ทุกคนมี key
- Server อ่านห้องและประวัติจากข้อมูลของตัวเอง ไม่รับประวัติทั้งหมดจาก Browser มาใช้เป็นแหล่งข้อมูลหลัก
- ห้องส่วนตัวตรวจคู่สมาชิก ส่วนกลุ่มตรวจสมาชิกปัจจุบันและกรอง `visible_to` ด้วยกติกาเดิม คนเพิ่ง Join หรือ Leave แล้วกลับเข้าไม่ควรได้ข้อมูลที่ตัวเองไม่มีสิทธิ์ผ่านสรุป
- หากไม่มีข้อความที่มีสิทธิ์ ไม่เรียก API
- ตรวจสิทธิ์กลุ่มซ้ำก่อนคืนผล หากผู้ขอ Leave ระหว่างรอ AI ต้องไม่แสดงผลสรุปนั้น ส่งกลับเฉพาะ session ที่ร้องขอ ไม่ส่งไปยังคนที่ใช้ชื่อเดิมบนการเชื่อมต่อใหม่
- อ่าน snapshot แล้วปล่อย Lock ก่อนเรียก API ใช้งานเบื้องหลังที่จำกัดจำนวนและมี timeout เพื่อให้การส่ง/รับแชตทำงานต่อได้ ไม่เรียก Groq ขณะถือ state lock หรือ room lock
- ข้อความในแชตเป็นข้อมูลให้สรุป ไม่ใช่คำสั่งใหม่ที่ AI ต้องทำตาม แยกคำสั่งระบบออกจากเนื้อหาแชต และไม่เปิด tool execution ให้โมเดลสำหรับงานนี้
- ข้อเสนอคำสั่ง: `summarize_room` และผล `room_summary` พร้อมชนิดห้อง รหัสห้อง และ `request_id` ชื่อ/schema สุดท้ายจะกำหนดก่อนเขียน

## 5. ลำดับการทำงาน

### ขั้นที่ 1: ตกลงพฤติกรรม

เลือกขอบเขตข้อความ ภาษา วิธีแสดงผล และการบันทึกตามข้อเสนอในหัวข้อ 2 จากนั้นทดลอง prompt กับบทสนทนาจำลองที่รู้คำตอบ

ผลที่ต้องได้: ตัวอย่าง input/output ที่ยอมรับได้และนโยบายที่ตกลงร่วมกัน

### ขั้นที่ 2: เตรียม Groq

1. ผู้ใช้สร้างบัญชี GroqCloud และ API key ด้วยตัวเอง
2. ตั้ง `GROQ_API_KEY` บนเครื่อง Server ผ่าน environment ไม่ใส่ใน JavaScript, Git หรือแชตนี้
3. กำหนด `GROQ_MODEL` จากโมเดลที่บัญชีเรียกใช้ได้ ทดสอบการสรุปภาษาไทย และดู rate limits จริง
4. เพิ่ม SDK ใน `requirements.txt` และติดตั้งใน `.venv` เมื่อเริ่มเขียนส่วนนี้
5. ทดลองข้อความจำลองสั้น ๆ ให้รับผลได้ก่อนต่อประวัติจริง

`.gitignore` มี `.env` อยู่แล้ว แต่การสร้างไฟล์ `.env` ไม่ทำให้ Python โหลดค่าเอง ถ้าเลือกใช้ไฟล์นี้ต้องเพิ่มตัวโหลดให้ชัดเจน หรือเริ่มด้วย environment variable โดยตรง

ผลที่ต้องได้: เรียก AI จาก Python ได้โดยไม่เปิดเผย key

### ขั้นที่ 3: เขียนโมดูลสรุป

เขียนโมดูลในแพ็กเกจ `feature/summarize/` แยก `ai_summarize.py` สำหรับ API และ `service.py` สำหรับเตรียมข้อความ/คำสั่งสรุป ใช้ตัวแทน API ในการทดสอบเพื่อไม่เสียโควตาทุกครั้ง

ผลที่ต้องได้: รับรายการข้อความที่อนุญาตแล้วและคืนสรุป หรือคืนข้อผิดพลาดที่เข้าใจได้

รายละเอียดโมดูล: จำกัดไม่เกิน 30 ข้อความและ JSON input 6,000 UTF-8 bytes โดยลดข้อความเก่าทั้งรายการ ไม่ตัดกลางข้อความ ถ้าข้อความล่าสุดเพียงรายการเดียวเกินขนาดให้คืนข้อผิดพลาด ผลลัพธ์ระบุจำนวนข้อความ ID แรก/สุดท้าย และสถานะว่ามีข้อความถูกตัดออกจากช่วงหรือไม่ เพดาน bytes เป็นการจำกัดขนาดข้อมูล ไม่ใช่การรับรองจำนวน token หรือโควตาของบัญชี

### ขั้นที่ 4: ต่อ Socket และ Server

เพิ่มคำสั่งผ่าน bridge/NetworkClient ไปยัง Server ตรวจสิทธิ์ เลือก snapshot ของห้อง แล้วมอบงานให้ worker ที่จำกัดจำนวน คืนผลให้ผู้ขอด้วย request_id โดยไม่ถือ Lock ขณะรอ API และไม่กระจายผลให้สมาชิกคนอื่น

ผลที่ต้องได้: สรุปได้เฉพาะห้องและข้อความที่ผู้ขอมีสิทธิ์ ขณะรอ AI คนอื่นยังแชตได้

### ขั้นที่ 5: เพิ่มหน้าเว็บ

เพิ่มปุ่ม Summarize และพื้นที่แสดงผลต่อห้อง มีสถานะกำลังสรุป ป้องกันกดซ้ำ และข้อผิดพลาด เช่น ไม่มี key, API ไม่ตอบ หรือเต็มโควตา เมื่อสลับห้องให้ผลกลับห้องต้นทางตาม request_id และไม่แสดงซ้ำในแชตปกติ

ผลที่ต้องได้: ผู้ใช้กดสรุปจากห้องจริงได้ โดยการแชตเดิมยังทำงาน

### ขั้นที่ 6: ทดสอบและเตรียมเดโม

- ภาษาไทย/อังกฤษ ข้อความสั้น ยาว ว่าง และบทสนทนาที่ไม่มีข้อตกลง
- คนที่ไม่อยู่ในห้องหรือไม่เป็นสมาชิกกลุ่มต้องสรุปไม่ได้
- สมาชิกใหม่ไม่เห็นข้อมูลก่อน Join ผ่านสรุป และคนที่กลับเข้าไม่เห็นช่วงที่ Leave ไป
- Leave/Disconnect ระหว่างสรุปไม่ทำให้ผลรั่วไปหาคนอื่นหรือ session ใหม่
- ระหว่าง AI ทำงานยังส่งและรับข้อความได้ สรุปหลายห้องไม่ปนกันและไม่สร้าง worker ได้ไม่จำกัด
- API key ผิด timeout, 429 และบริการล่ม ไม่ทำให้ TCP Server หรือแชตปกติหยุด
- ตรวจคุณภาพผลจากตัวอย่างที่รู้คำตอบ และมีเดโมเรียก Groq จริงโดยผู้ใช้ตั้ง key แล้ว การทดสอบด้วยตัวแทน API อย่างเดียวไม่ใช่เดโม AI จริง
- ตรวจ regression ของ Part 2 และเตรียมสไลด์เส้นทาง Socket กับ HTTPS/API ให้แยกกันชัดเจน
