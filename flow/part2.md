## 3. แนวทางออกแบบที่เสนอ

รายละเอียดต่อจากนี้เป็นวิธีที่เราเสนอเพื่อทำตามโจทย์ ไม่ใช่ข้อกำหนดเพิ่มเติมจากอาจารย์ การตัดสินใจที่ยังไม่ชัดเจนอยู่ในหัวข้อ 9 และต้องคุยกันก่อนเขียนส่วนนั้น

### หน้าเว็บ Client

เลือกหน้าเว็บ HTML, Tailwind CSS และ JavaScript พื้นฐาน โดยใช้ Python bridge (`aiohttp`) เชื่อม WebSocket จาก Browser ไปยัง `NetworkClient` และ TCP Server เดิม ไม่เพิ่ม React หรือฐานข้อมูลในขั้นนี้

```text
Client computer A: Browser A <-> WebSocket <-> Python bridge A <-> TCP <-> Server
Client computer B: Browser B <-> WebSocket <-> Python bridge B <-> TCP <-> Server
```

ระหว่างพัฒนาเปิดหลายแท็บผ่าน bridge เดียวบนเครื่องเดียวได้ แต่ละแท็บมี `NetworkClient` และ TCP Socket ของตัวเอง ส่วนการเดโมข้ามเครื่องให้รัน bridge ภายในเครื่อง Client แต่ละเครื่อง แล้วกรอก IP ของ TCP Server เป็นปลายทาง พอร์ตเว็บเริ่มต้นคือ `8765` ส่วน TCP Server ใช้ `5000`

### รูปแบบหน้าจอ

- ใช้โทนมืดเทาเข้ม เส้นขอบเทาหม่น และสีน้ำเงินหม่นสำหรับแท็บหรือปุ่มที่เลือก ตามภาพตัวอย่างที่ตกลง
- หัวแอปแสดง Socket Chat ชื่อผู้ใช้ และสถานะ Offline, Connecting, Online หรือ Error
- แถบเชื่อมต่อมี Server address, Port, Your name พร้อมปุ่ม Connect และ Disconnect
- ด้านซ้ายแสดง Online users พร้อมจำนวน รวมชื่อตัวเอง และส่วน Groups พร้อมสมาชิก
- ด้านขวามีแท็บห้อง ชื่อห้อง พื้นที่ข้อความ และช่อง Message พร้อมปุ่ม Send
- เมื่อมีข้อความในขั้นที่เกี่ยวข้อง ให้แสดงข้อความเข้าอยู่ซ้ายและข้อความของตัวเองอยู่ขวา
- หน้าจอย่อได้ โดยหน้าจอเล็กเรียงส่วนรายชื่อและพื้นที่ห้องลงด้านล่าง ไม่ให้ฟอร์มล้นแนวนอน
- โครงหน้าจอใช้ข้อมูลจริงจาก Server ส่วนห้องหรือกลุ่มที่ยังไม่ทำให้แสดงพื้นที่ว่างและปิดปุ่ม ไม่ใส่ข้อความตัวอย่างปนกับข้อมูลจริง

- หน้าเริ่มต้นมีช่องชื่อและข้อมูล Server สำหรับเชื่อมต่อ
- รายชื่อผู้ใช้ออนไลน์แสดงทุกคน รวมตัวเอง โดยเลือกคนอื่นเพื่อเปิดห้องส่วนตัว
- รายการกลุ่มแสดงทุกกลุ่มและสมาชิก พร้อมปุ่มสร้างกลุ่ม Join และ Leave Group โดยแยกสถานะออนไลน์ออกจากการเป็นสมาชิก
- ใช้แท็บแยกห้องส่วนตัวและห้องกลุ่ม
- ทุกแท็บมีพื้นที่ข้อความ ช่องพิมพ์ และปุ่ม Send ของห้องนั้น
- การเลือกดูกลุ่มไม่ถือว่าเข้าร่วม สมาชิกใหม่ต้องกด Join เอง ส่วนสมาชิกเดิมที่กลับมาใช้ชื่อเดิมจะใช้ห้องเดิมต่อได้
- แสดงข้อความใหม่ในห้องที่ถูกต้อง แม้ผู้ใช้กำลังเปิดดูอีกห้อง

ใช้ Tailwind CLI สร้าง CSS จาก class ใน HTML/JavaScript ก่อนเปิดแอป Node.js ใช้เฉพาะการ build สไตล์ ไม่ใช่ TCP Server ส่วน Browser โหลด HTML, JavaScript และ CSS จาก bridge ภายในเครื่อง Tkinter เดิมเก็บไว้เป็นตัวอย่างและไม่ได้เป็นหน้าหลักของแผนต่อไป

### การแบ่งหน้าที่

| ส่วน | หน้าที่ |
| --- | --- |
| Server | เก็บคนออนไลน์ ห้อง สมาชิก ตรวจสิทธิ์ และส่งข้อมูลไปยังผู้รับที่ถูกต้อง |
| Browser UI | HTML จัดโครงหน้า Tailwind จัดสไตล์ JavaScript รับคำสั่งและอัปเดต DOM ตามเหตุการณ์จาก WebSocket |
| Python bridge | เสิร์ฟหน้าเว็บภายในเครื่อง และแปลงช่องทาง WebSocket ของแต่ละแท็บเป็นการเรียก `NetworkClient` โดยไม่เก็บสิทธิ์หรือสมาชิกแทน Server |
| งานเครือข่ายของ Client | `NetworkClient` ติดต่อ TCP Socket ผ่าน sender/receiver thread และคิวเดิม |
| Protocol | ส่งและแยก JSON ให้ครบข้อความเหมือนกันทั้งสองฝั่ง |

Browser ส่งคำสั่งผ่าน WebSocket ให้ bridge แล้ว bridge เรียก `NetworkClient.send()` เพื่อใส่คิว `outgoing` ส่วน sender thread ส่ง JSON ผ่าน TCP เมื่อ receiver thread รับข้อมูล จะใส่คิว `events` แล้วงาน async ของ bridge ตรวจคิวโดยไม่รอและส่งต่อผ่าน WebSocket JavaScript ใช้เหตุการณ์ `message` อัปเดต DOM จึงไม่มีการใช้ Tkinter widget หรือ `after()` ในเส้นทางเว็บ

แต่ละแท็บแยก session, คิว และ TCP Socket เมื่อปิดแท็บ กด Disconnect หรือ bridge ปิด ต้องปิด Socket และหยุด worker ของแท็บนั้น การเชื่อมต่อใหม่สร้าง `NetworkClient` ใหม่และเริ่ม version รายชื่อใหม่ ไม่ใช้เหตุการณ์ค้างจาก session เก่า ส่วนการปิด bridge ต้องไม่ทำให้ TCP Server หยุด

### ห้องและสิทธิ์

- Server เป็นผู้กำหนด `room_id` และเก็บสมาชิกจริงของห้อง ไม่เชื่อรายชื่อสมาชิกที่ Client แนบมาเอง
- ห้องส่วนตัวผูกกับคู่ผู้ใช้ ไม่สร้างห้องซ้ำเมื่ออีกฝ่ายเปิดแชตกลับมา
- ห้องกลุ่มมี `group_id` คงที่สำหรับอ้างอิง แยกจากชื่อที่ใช้แสดง
- อนุญาตให้ชื่อกลุ่มซ้ำกัน โดยแยกด้วย `group_id` และแสดงรหัสให้แยกกลุ่มใน GUI ได้ รหัสกลุ่มใหม่ต้องไม่ชนกับกลุ่มเก่าหรือประวัติที่เก็บไว้
- ทุกคนเห็น metadata ของกลุ่มและรายชื่อสมาชิกได้ตาม R9 แต่การเห็นรายการไม่ได้ให้สิทธิ์รับหรือส่งข้อความในกลุ่ม
- ตรวจสิทธิ์ที่ Server ทุกครั้ง แม้ Client จะส่งคำสั่งเองโดยไม่ผ่านปุ่มบน GUI
- ใช้สถานะจาก Server เป็นหลัก เพื่อให้รายชื่อและสมาชิกตรงกันทุก Client
- เก็บสมาชิกกลุ่มแยกจากการเชื่อมต่อ การหลุด ปิด Client หรือปิด Server ทำให้เป็นออฟไลน์ แต่ไม่ใช่การออกจากสมาชิก
- การคืนสมาชิกเมื่อกลับมาใช้ชื่อเดิมอ้างอิงการ Join ที่ผู้ใช้นั้นเคยเลือกเอง ไม่เพิ่มสมาชิกใหม่โดยผู้สร้างกลุ่ม
- สมาชิกออกจากกลุ่มด้วย Leave Group เท่านั้น เมื่อสมาชิกคนสุดท้ายออกจึงลบกลุ่ม ผู้สร้างออกก่อนคนอื่นไม่ทำให้กลุ่มถูกลบ

### ประวัติแชตและไฟล์ข้อมูล

- เก็บข้อมูลที่กำลังใช้งานในหน่วยความจำ และบันทึกกลุ่ม สมาชิก รหัสห้อง และประวัติเป็นไฟล์ภายใน `output/` ของโปรเจกต์ตามที่เลือก โดยยังไม่เพิ่มฐานข้อมูล
- `output/` อยู่ภายในโฟลเดอร์โปรเจกต์ ไม่ใช่ไดเรกทอรี `/output` ของระบบ และถูกละเว้นด้วย `.gitignore`
- ให้ Server เก็บสถานะหลัก เพื่อให้กลับมาใช้ชื่อเดิมจาก Client เครื่องอื่นและคุยต่อในกลุ่มเดิมได้ เสนอให้ใช้ไฟล์เช่น `output/chat_state.json` โดยชื่อไฟล์และ schema จะกำหนดก่อนเขียนส่วนจัดเก็บ
- เก็บชื่อผู้ใช้ รหัสห้อง และสิทธิ์เห็นข้อความในขณะที่ส่ง เพื่อคืนประวัติให้เฉพาะชื่อที่มีสิทธิ์เดิม ไม่ส่งประวัติทั้งหมดให้ทุก Client
- คนที่เพิ่งเข้ากลุ่มเริ่มรับข้อความตั้งแต่เข้าร่วม ไม่ได้รับประวัติช่วงก่อนเข้ากลุ่มโดยอัตโนมัติ
- เมื่อเปิด Server ใหม่ ให้โหลดกลุ่ม สมาชิก รหัสห้องเดิม และประวัติกลับมา ส่วนรายชื่อออนไลน์เริ่มจากว่างแล้วเปลี่ยนตาม Client ที่เชื่อมต่อจริง
- เมื่อกลับมาใช้ชื่อเดิม คืนกลุ่มเดิมที่ยังเป็นสมาชิกและประวัติที่ชื่อนั้นมีสิทธิ์เห็น รวมข้อความที่ส่งระหว่างออฟไลน์ขณะที่ยังเป็นสมาชิก โดยไม่รวมข้อความก่อน Join หรือหลัง Leave
- การส่งสดส่งให้เฉพาะสมาชิกที่ออนไลน์ ส่วนประวัติที่คืนภายหลังตรวจสิทธิ์ตามช่วงสมาชิก ไม่ส่งข้อความกลุ่มให้ผู้ที่ไม่เคยเข้าร่วม
- การเขียนไฟล์จาก Server หลาย thread ต้องป้องกันการเขียนชนกัน และไม่ปล่อยไฟล์ JSON ที่เขียนไม่ครบแทนไฟล์ประวัติเดิม
- ชื่อเป็นตัวตนของระบบในขอบเขตนี้ เมื่อชื่อว่าง ใครที่ลงทะเบียนด้วยชื่อนั้นจะเห็นประวัติตามชื่อนั้นได้ ระบบนี้ยังไม่มีรหัสผ่านยืนยันว่าเป็นบุคคลเดิม

4. กำหนดคำสั่งและเหตุการณ์ JSON ที่ต้องเพิ่ม โดยเก็บชื่อคำสั่งเป็นภาษาอังกฤษ

### ขั้นที่ 2: รายชื่อผู้ใช้ออนไลน์ — R3, R4

1. ต่อยอดการตรวจชื่อซ้ำ และให้ GUI แสดงเหตุผลเมื่อชื่อใช้ไม่ได้
2. หลังลงทะเบียนสำเร็จ ให้ Client ได้รายชื่อผู้ใช้ออนไลน์ทั้งหมด รวมตัวเอง
3. เมื่อมีคนเข้า ออก หรือหลุด ให้ Server ส่งรายชื่อที่อัปเดตไปยัง Client ที่เหลือ
4. ให้ GUI อัปเดตรายการโดยไม่ต้องเชื่อมต่อใหม่
5. จัดลำดับการลงทะเบียนและการอัปเดตให้ Client ไม่เห็นรายการเก่าย้อนทับรายการใหม่

ผลที่ต้องเห็น: เปิด alice, bob และ carol ในคนละแท็บ แล้วทุกคนเห็นรายชื่อครบ เมื่อ carol กด Disconnect หรือปิดแท็บ อีกสองคนเห็นรายการเปลี่ยนตามจริง โดยแต่ละแท็บไม่ใช้ session ร่วมกัน

### ขั้นที่ 3: ห้องส่วนตัวและหน้าต่างแชต — R5, R6, R7

1. เมื่อเลือกผู้ใช้จากรายชื่อ ให้ขอเปิดห้องส่วนตัวผ่าน Server
2. ให้ Server สร้างหรือคืนห้องเดิมของคู่นั้น ตรวจสิทธิ์ดูห้องและประวัติ ส่วนการส่งข้อความใหม่ต้องตรวจว่าผู้รับติดต่อได้
3. สร้างแท็บที่มีหน้าต่างข้อความ ช่องพิมพ์ และปุ่ม Send ของตัวเอง
4. ใส่ `room_id` ในเหตุการณ์ข้อความ เพื่อให้แสดงเข้าห้องถูกต้อง
5. แสดงทั้งข้อความของผู้ส่งและข้อความที่ได้รับ โดยกำหนดจุดเพิ่มข้อความให้ชัดเจนเพื่อไม่แสดงซ้ำจากข้อความตอบรับ
6. Server ส่งเนื้อหาเฉพาะคู่สนทนา และปฏิเสธคำสั่งที่พยายามใช้ห้องของคนอื่น

ผลที่ต้องเห็น: alice คุยกับ bob และ carol คนละห้องได้ ข้อความไม่ปนกัน และคนที่ไม่ใช่คู่สนทนาไม่ได้รับเนื้อหา

### ขั้นที่ 4: สร้างและแสดงรายการกลุ่ม — R8, R9

1. ทุก Client มีปุ่ม Create Group และสร้างได้มากกว่าหนึ่งกลุ่ม
2. เมื่อ Server สร้างกลุ่ม ให้เพิ่มสมาชิกเพียงผู้สร้างคนเดียว
3. ส่งรายการกลุ่มทั้งหมดพร้อมสมาชิกให้ทุก Client รวมคนที่ยังไม่ได้เข้ากลุ่ม
4. เมื่อมี Client เข้ามาทีหลัง ต้องได้รับรายการกลุ่มที่มีอยู่ด้วย
5. อัปเดต metadata เมื่อกลุ่มหรือสมาชิกเปลี่ยน โดยไม่กระจายเนื้อหาแชตไปกับรายการนี้

ผลที่ต้องเห็น: alice สร้างกลุ่ม ทุกคนเห็นกลุ่มและเห็นสมาชิกเป็น alice คนเดียว

### ขั้นที่ 5: เข้ากลุ่มด้วยตัวเอง — R10

1. ผู้ใช้เลือกกลุ่มและกด Join ด้วยตัวเอง
2. Server อ้างอิงผู้ขอเข้าร่วมจากการเชื่อมต่อ ไม่รับคำสั่งเพิ่มผู้ใช้อีกคนแทน
3. เมื่อยืนยันสมาชิกแล้ว จึงเปิดให้ใช้ห้องกลุ่ม
4. แจ้งรายชื่อสมาชิกใหม่ให้ทุก Client เพื่อให้รายการตาม R9 ตรงกัน
5. การกด Join ซ้ำไม่เพิ่มสมาชิกซ้ำ
6. สมาชิกเดิมที่ออฟไลน์แล้วกลับมาใช้ชื่อเดิมยังเป็นสมาชิก ไม่ต้อง Join ใหม่ การกด Leave Group จึงจะออกจากสมาชิกจริง

ผลที่ต้องเห็น: bob ไม่ถูกเพิ่มตอน alice สร้างกลุ่ม แต่ถูกเพิ่มเมื่อ bob กด Join เอง และทุกคนเห็นรายชื่อสมาชิกอัปเดต

### ขั้นที่ 6: ข้อความกลุ่ม — R5, R6, R11

1. ทุกกลุ่มที่เข้าร่วมมีแท็บห้อง พร้อมช่องพิมพ์และหน้าต่างข้อความของกลุ่มนั้น
2. เมื่อส่ง ให้ Server ตรวจว่ากลุ่มมีอยู่และผู้ส่งเป็นสมาชิกจริง
3. ส่งข้อความเฉพาะสมาชิกกลุ่ม และแสดงข้อความของผู้ส่งเองในห้องด้วย
4. คนที่เห็นกลุ่มในรายการแต่ไม่ได้เข้าร่วมต้องไม่ได้รับเนื้อหา
5. ห้องส่วนตัวและหลายห้องกลุ่มต้องแสดงข้อความแยกกันได้

ผลที่ต้องเห็น: alice และ bob คุยในกลุ่มได้ ส่วน carol เห็นชื่อกลุ่มและสมาชิก แต่ไม่ได้รับข้อความจนกว่าจะเข้าร่วม

### ขั้นที่ 7: การออก การหลุด และการทำงานพร้อมกัน

1. อัปเดตรายชื่อออนไลน์เมื่อ Client ออกหรือหลุด
2. เมื่อ Client หลุดหรือปิดโปรแกรม ให้เก็บสมาชิกกลุ่มไว้และแสดงสถานะออฟไลน์ การกด Leave Group จึงลบจากสมาชิก และลบกลุ่มเมื่อสมาชิกคนสุดท้ายออก
3. แสดงสถานะเมื่อคู่สนทนาหรือ Server หลุด โดย GUI ยังตอบสนองและปิดได้
4. ปิด Socket งานเบื้องหลัง และ WebSocket เมื่อปิดแท็บหรือ bridge โดยไม่ปล่อย thread ค้าง
5. ตรวจการสร้างกลุ่ม เข้าร่วม และส่งพร้อมกัน โดยใช้ Lock ป้องกันข้อมูลชนกันและไม่ถือกุญแจสถานะระหว่างรอเครือข่าย
6. บันทึกสถานะกลุ่ม สมาชิก รหัสห้อง และประวัติลง `output/` และโหลดกลับเมื่อเปิด Server ใหม่ โดยไม่บันทึก Socket หรือสถานะออนไลน์เดิมให้กลายเป็นออนไลน์ปลอม

ผลที่ต้องเห็น: คนหนึ่งหลุดไม่ทำให้ Server หรือ Client ที่เหลือหยุดทำงาน รายชื่อออนไลน์ตรงตามจริง กลุ่มยังอยู่เมื่อทุกคนออฟไลน์ และเปิด Server ใหม่แล้วสมาชิกเดิมกลับมาคุยต่อในกลุ่มเดิมได้

### ขั้นที่ 8: ทดสอบครบข้อและเตรียมเดโม

1. รันทดสอบเดิม เพื่อยืนยันว่าการรับส่ง TCP และ UTF-8 ยังถูกต้อง
2. เพิ่ม integration tests สำหรับรายชื่อ ห้อง กลุ่ม และการปฏิเสธผู้ไม่มีสิทธิ์
3. ทดลอง Browser จริงหลายแท็บ ให้แต่ละห้องมีทั้งช่องพิมพ์และหน้าต่างข้อความ และสลับห้องได้โดยข้อความไม่ปน รวมถึงเชื่อมต่อใหม่หลังชื่อซ้ำ Server ปิด หรือ bridge ปิด
4. ใช้ Client อย่างน้อยสามคนในสถานการณ์ทดสอบ เพื่อพิสูจน์ว่าเนื้อหาไม่รั่วไปหาคนนอกห้อง จำนวนนี้เป็นวิธีทดสอบ ไม่ใช่ข้อกำหนดว่าต้องมีคอมจริงสามเครื่อง
5. เตรียมเดโมและสไลด์อธิบาย R3–R11 ควบคู่กับการทำ Part 1 ให้ครบก่อนตรวจคะแนน

## 5. คำสั่ง JSON ที่เสนอให้เพิ่ม

ชื่อและ schema ต่อไปนี้เป็นข้อเสนอสำหรับตกลงก่อนเขียน ไม่ใช่ API ที่สร้างแล้ว

| คำสั่งหรือเหตุการณ์ | หน้าที่ |
| --- | --- |
| `register`, `registered` | ใช้ต่อสำหรับลงชื่อและยืนยันการเชื่อมต่อ |
| `users_updated` | รายชื่อออนไลน์ทั้งหมด รวมผู้รับข้อมูลเอง |
| `open_private`, `room_opened` | ขอเปิดห้องส่วนตัวและรับข้อมูลห้องที่ Server ตรวจสอบแล้ว |
| `create_group`, `group_created` | สร้างกลุ่มที่มีผู้สร้างคนเดียว |
| `groups_updated` | รายการกลุ่มทั้งหมดและสมาชิก โดยไม่มีเนื้อหาแชต |
| `join_group`, `group_joined` | ผู้ใช้ขอเข้ากลุ่มให้ตัวเองและรับผลยืนยัน |
| `leave_group`, `group_left` | ผู้ใช้ขอออกจากสมาชิกกลุ่มของตัวเอง โดยไม่ใช่แค่ปิดการเชื่อมต่อ |
| `private_message`, `group_message` | ส่งและรับเนื้อหาตามชนิดห้อง โดยมีรหัสห้องกำกับ |
| `sent`, `error` | แจ้งผลการส่งหรือข้อผิดพลาดให้สัมพันธ์กับคำขอ |

การยืนยัน `sent` หมายถึง Server ส่งต่อผ่าน Socket แล้ว ไม่ใช่สถานะอ่านแล้ว ต้องกำหนดว่าข้อความของผู้ส่งจะปรากฏจากเหตุการณ์ใดเพียงครั้งเดียวก่อนเชื่อม GUI

## 6. โครงสร้างไฟล์ที่เสนอ

| ไฟล์ | สิ่งที่จะทำ |
| --- | --- |
| `server.py` | เพิ่มรายชื่อ ห้องส่วนตัว กลุ่ม สมาชิก และการตรวจสิทธิ์ |
| `protocol.py` | ใช้การส่งและแยก JSON ร่วมกันต่อไป |
| `client.py` | เก็บ Terminal client สำหรับทดลองและตรวจปัญหาเครือข่ายตามที่ตกลงก่อนเริ่ม GUI |
| `client_network.py` | งาน TCP และคิวเหตุการณ์ที่ bridge เรียกใช้ร่วมกับ Client เดิม |
| `web_bridge.py` | เปิดเว็บภายในเครื่องและดูแล WebSocket แยกตามแท็บ พร้อมส่งต่อไปยัง NetworkClient |
| `web/index.html` | โครงหน้าจอโทนมืด ฟอร์มเชื่อมต่อ รายชื่อ กลุ่ม และพื้นที่ห้อง |
| `web/app.js` | คำสั่งจากผู้ใช้ WebSocket และการอัปเดต DOM |
| `web/input.css` | นำเข้า Tailwind และกำหนดสีหลักของแอป |
| `web/assets/styles.css` | CSS ที่ Tailwind สร้างใหม่ได้และละเว้นจาก Git |
| `package.json`, `package-lock.json` | dependency และคำสั่ง build/watch ของ Tailwind |
| `requirements.txt` | dependency Python สำหรับ bridge |
| `gui_client.py` | เก็บ GUI Tkinter เดิมเป็นตัวอย่าง ไม่ใช่หน้าหลักสำหรับต่อยอด |
| `state_store.py` | เสนอให้แยกการอ่านและบันทึกกลุ่ม สมาชิก และประวัติ พร้อมกรองสิทธิ์ก่อนคืนให้ Client |
| `output/` | ข้อมูลกลุ่ม สมาชิก และประวัติที่โปรแกรมสร้างและบันทึก ถูกละเว้นจาก Git |
| `tests/test_chat.py` | ต่อยอดการทดสอบการเชื่อมต่อและเพิ่มกรณี Part 2 โดยแยกไฟล์เพิ่มเติมเมื่อจำเป็น |
| `tests/test_web_bridge.py` | ทดสอบ Browser commands ผ่าน WebSocket กับ TCP Server จริง การแยกแท็บ และการปิดการเชื่อมต่อ |
| `README.md` | วิธีเปิด GUI เดโม และผลการทดสอบตามพฤติกรรมที่ทำจริง |
| `flow/part2.md` | แผนหลักของ Part 2 โดยไม่ใช้บันทึกความคืบหน้า |

โครงสร้างไฟล์โปรแกรมนี้ยังเป็นข้อเสนอ ส่วน `output/` เป็นตำแหน่งข้อมูลที่ตกลงให้ละเว้นจาก Git

## 7. ตารางตรวจรับตาม Requirement

| ข้อ | สถานการณ์ทดสอบที่ต้องผ่าน |
| --- | --- |
| R3 | สอง Client ขอชื่อเดียวกันพร้อมกันได้สำเร็จเพียงคนเดียว อีกคนเลือกชื่อใหม่ได้ |
| R4 | ทุกคนเห็นรายชื่อครบ รวมตัวเอง และอัปเดตเมื่อมีคนเข้าออก |
| R5 | ห้อง alice–bob แยกจาก alice–carol และแต่ละกลุ่มมีห้องของตัวเอง |
| R6 | ทุกห้องพิมพ์และส่งได้ แสดงทั้งข้อความของตัวเองและข้อความเข้าถูกห้อง |
| R7 | alice เลือก bob จากรายชื่อเพื่อส่งส่วนตัวได้ carol ไม่ได้รับเนื้อหา และการปลอมรหัสห้องถูกปฏิเสธ |
| R8 | ทุกคนสร้างกลุ่มได้ และกลุ่มใหม่มีสมาชิกเพียงผู้สร้าง |
| R9 | ทุกคนรวมถึงคนเข้าทีหลังเห็นกลุ่มทั้งหมดพร้อมสมาชิกที่ตรงกัน |
| R10 | ไม่มีการเพิ่มสมาชิกอัตโนมัติ ผู้ใช้ Join เองได้ และเพิ่มคนอื่นแทนตัวเองไม่ได้ |
| R11 | สมาชิกส่งและรับข้อความกลุ่มได้ คนนอกส่งไม่ได้และไม่ได้รับเนื้อหา แม้ส่งคำสั่งเอง |

ทดสอบเสริมเมื่อฟีเจอร์เกี่ยวข้องพร้อมแล้ว: หลายคนส่งพร้อมกัน ข้อความไทยและข้อความยาว ข้อมูลมาไม่ครบหรือหลายข้อความรวมกัน ชื่อกลุ่มหรือผู้ใช้มีช่องว่าง การเข้ากลุ่มซ้ำ การหลุดระหว่างส่ง และสถานะล่าสุดเมื่อมีหลายเหตุการณ์ใกล้กัน รวมถึงประวัติเมื่อใช้ชื่อเดิม การกรองประวัติตามช่วงสมาชิก และกลุ่มชื่อซ้ำที่มีคนละ `group_id`

กรณีทดสอบนโยบายกลุ่มที่เลือก:

- ปิด Client ทุกคนแล้วกลุ่มและสมาชิกยังอยู่ แต่รายชื่อออนไลน์ว่าง
- ปิดและเปิด Server ใหม่ กลุ่มเดิมมี `group_id` และสมาชิกเดิม สมาชิกที่กลับมาใช้ชื่อเดิมส่งข้อความต่อได้
- ผู้สร้างกด Leave Group แต่ยังมีสมาชิกคนอื่น กลุ่มยังอยู่
- สมาชิกคนสุดท้ายกด Leave Group กลุ่มถูกลบจากรายการ แม้ก่อนหน้านั้นทุกคนจะออฟไลน์ก็ไม่ถือว่ากลุ่มว่าง
- คนที่ Leave แล้วไม่ได้รับข้อความใหม่หรือประวัติช่วงหลัง Leave ส่วนคนที่ไม่เคย Join ไม่ได้ประวัติก่อนเข้าร่วม

## 9. นโยบายที่เลือกและจุดที่ต้องยืนยันก่อนเขียน

| เรื่อง | นโยบาย |
| --- | --- |
| หน้าต่าง | หน้าเว็บ HTML + Tailwind CSS + JavaScript โทนมืดตามภาพ พร้อม Python bridge ภายในเครื่องและ TCP Server เดิม |
| ประวัติแชต | ใช้หน่วยความจำระหว่างทำงานและบันทึกไฟล์ใน `output/` ที่ละเว้นจาก Git โดยยังไม่เพิ่มฐานข้อมูล |
| ข้อความก่อนเข้ากลุ่ม | เริ่มรับตั้งแต่เข้าร่วม ไม่ดึงประวัติก่อนหน้าให้สมาชิกใหม่อัตโนมัติ |
| คนหลุดหรือกลับมาใช้ชื่อเดิม | อนุญาตให้ชื่อเดิมที่ว่างแล้วได้ประวัติที่ชื่อนั้นเคยเห็น แยกประวัติออกจาก Socket และสถานะออนไลน์ |
| สมาชิกกลุ่มเมื่อหลุด | เก็บสมาชิกไว้และเปลี่ยนเป็นออฟไลน์ เมื่อกลับมาใช้ชื่อเดิมจะใช้กลุ่มเดิมต่อได้ ไม่ต้อง Join ใหม่ |
| ปิดและเปิด Server ใหม่ | โหลดกลุ่ม สมาชิก รหัสห้องเดิม และประวัติกลับมา ส่วนรายชื่อออนไลน์อ้างอิงการเชื่อมต่อใหม่เท่านั้น |
| ผู้สร้างออกและกลุ่มว่าง | Leave Group คือการออกจากสมาชิก ลบกลุ่มเมื่อสมาชิกคนสุดท้าย Leave เท่านั้น ผู้สร้างออกก่อนคนอื่นหรือทุกคนออฟไลน์ไม่ทำให้กลุ่มถูกลบ |
| ชื่อกลุ่มซ้ำ | อนุญาตชื่อซ้ำและแยกแต่ละกลุ่มด้วย `group_id` |

นโยบายกลุ่มข้างต้นเลือกแบบเก็บกลุ่มและประวัติข้ามการปิด Server แล้ว ส่วนรายละเอียดที่ยังต้องกำหนดก่อนเขียนคือรูปแบบไฟล์และการเก็บหรือลบประวัติเมื่อกลุ่มถูกลบจริงจากการ Leave ของสมาชิกคนสุดท้าย การลบกลุ่มจริงต่างจากการออฟไลน์หรือปิด Server ให้ดำเนินการทีละขั้นพร้อมอธิบายว่าทำอะไรและทำเพื่ออะไร
