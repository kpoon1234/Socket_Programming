## 3. สถาปัตยกรรมเป้าหมาย

```text
คอมพิวเตอร์จริงเครื่องที่ 1             คอมพิวเตอร์จริงเครื่องที่ 2
         Client 1                              Client 2
             |                                     |
             +--------- TCP ผ่านอินเทอร์เน็ต --------+
                               |
                       Server บน Cloud
```

- Client ทั้งสองเครื่องไม่จำเป็นต้องอยู่ Wi-Fi เดียวกัน
- ทั้งสองเครื่องต้องติดต่อ Public IP หรือโดเมนของ Server และพอร์ตที่กำหนดได้
- Client ติดต่อ Server โดยตรง และ Server เป็นตัวกลางส่งต่อข้อความให้ผู้รับ

### เส้นทางข้อความ

```text
Client 1 ส่งข้อความ
    → Server รับข้อมูลและตรวจสอบผู้รับ
    → Server ส่งต่อให้ Client 2
    → Client 2 แสดงข้อความ

Client 2 ตอบกลับ
    → Server รับข้อมูลและตรวจสอบผู้รับ
    → Server ส่งต่อให้ Client 1
    → Client 1 แสดงข้อความ
```

## 5. Flow การทำงาน

### ขั้นที่ 1: เตรียมสภาพแวดล้อม

- เตรียม Python 3 บนเครื่องพัฒนาและเครื่อง Client ทั้งสองเครื่อง
- เลือก Cloud ที่รัน Python TCP Server ได้ และเปิดพอร์ต TCP ให้ Client เชื่อมต่อเข้ามาได้
- กำหนดพอร์ตของแอป เช่น `5000` โดยให้เปลี่ยนค่าได้
- ให้ Client รับค่า Server host และ port ตอนเริ่มโปรแกรม เพื่อสลับระหว่างทดสอบในเครื่องกับ Cloud ได้

### ขั้นที่ 2: ทดสอบ Client ↔ Server ในเครื่องเดียวก่อน

1. เขียน `server.py` ให้เปิด Socket และรอการเชื่อมต่อ
2. เขียน `client.py` ให้เชื่อมต่อ Server ที่ `127.0.0.1:5000`
3. ให้ Client ส่งข้อความ แล้ว Server ตอบกลับมาที่ Client คนเดิม
4. ตรวจสอบว่าส่งและรับข้อความภาษาไทยได้

ขั้นนี้เป็นการทดสอบการเชื่อมต่อพื้นฐาน ยังไม่ใช่การส่งต่อระหว่าง Client สองคน

คำสั่งหลักที่ต้องเข้าใจ:

```text
Server: socket() → bind() → listen() → accept()
Client: socket() → connect()
ส่งข้อมูล: sendall()
รับข้อมูล: recv()
ปิดการเชื่อมต่อ: close()
```

### ขั้นที่ 3: กำหนดรูปแบบและขอบเขตข้อความ

- ใช้ JSON หนึ่งข้อความต่อหนึ่งบรรทัด และเข้ารหัสเป็น UTF-8 ก่อนส่ง
- กำหนดชนิดคำสั่ง เช่น `register` และ `message`
- ให้ Client แจ้งชื่อเพื่อให้ Server ระบุการเชื่อมต่อของผู้รับได้ เป็นพื้นฐานสำหรับ R3 ใน Part 2
- ให้ Server อ้างอิงตัวตนผู้ส่งจากการเชื่อมต่อที่ลงทะเบียนไว้
- ใช้ buffer เก็บข้อมูลที่รับมา แล้วแยกเฉพาะข้อความที่ครบหนึ่งบรรทัดออกมาประมวลผล
- ทำส่วนนี้ใน `protocol.py` เพื่อให้ Client และ Server ใช้กติกาเดียวกัน

ตัวอย่างข้อมูลคำสั่งส่งข้อความจาก Client ไป Server:

```json
{"type": "message", "to": "client2", "text": "สวัสดี"}
```

JSON เป็นรูปแบบข้อมูล ส่วนกติกาคำสั่งและการแบ่งข้อความเป็นโปรโตคอลระดับแอปของเรา โดยใช้ TCP เป็นโปรโตคอลขนส่ง

**เหตุผลที่ต้องแบ่งข้อความเอง:** TCP ส่งข้อมูลเป็นกระแสไบต์ ไม่รับประกันว่า `recv()` หนึ่งครั้งจะได้ข้อความครบหนึ่งข้อความ อาจได้เพียงบางส่วนหรือได้หลายข้อความรวมกัน จึงต้องเก็บและแยกข้อมูลให้ถูกต้อง

### ขั้นที่ 4: รองรับ Client สองคนและส่งต่อข้อความ

1. ให้ Server กลับไปรอรับการเชื่อมต่อใหม่หลังรับ Client คนแรกแล้ว
2. แยก thread สำหรับรับข้อมูลจาก Client แต่ละคน
3. เก็บความสัมพันธ์ระหว่างชื่อ Client กับ Socket ที่เชื่อมต่ออยู่
4. เมื่อได้รับข้อความ ให้ Server ตรวจสอบผู้รับและส่งต่อผ่าน Socket ของคนนั้น
5. เมื่อ Client ปิดการเชื่อมต่อ ให้ลบออกจากรายการและปิด Socket โดย Server ยังทำงานต่อ
6. ป้องกันการแก้ข้อมูลร่วมกันหรือส่งข้อมูลเข้า Socket เดียวกันพร้อมกันจากหลาย thread

ทดสอบ Client สองตัวบนเครื่องเดียวได้ในช่วงพัฒนา แต่ต้องทดสอบและเดโมบนสองเครื่องจริงด้วย

### ขั้นที่ 5: นำ Server ขึ้น Cloud

1. เตรียมเครื่อง Cloud และ Python 3
2. นำไฟล์ที่ Server ต้องใช้ขึ้นไป
3. ตั้งค่า Server ให้ bind ที่ `0.0.0.0` และพอร์ตที่เลือก เช่น `5000`
4. อนุญาตการเชื่อมต่อเข้าผ่าน TCP พอร์ตนั้นใน Firewall ของ Cloud และระบบปฏิบัติการ
5. รัน Server และตรวจสอบว่ากำลังรอรับการเชื่อมต่อ
6. ตั้งค่า Client ให้เชื่อมต่อ Public IP หรือโดเมนของ Cloud ที่พอร์ตเดียวกัน

### ความหมายของ IP ที่ใช้

| ค่า | ความหมายและการใช้งาน |
| --- | --- |
| `127.0.0.1` | เครื่องตัวเอง ใช้เมื่อ Client และ Server อยู่บนเครื่องเดียวกัน |
| `0.0.0.0` ใน `bind()` | Server เปิดรับผ่านทุกที่อยู่ IPv4 ภายในเครื่องนั้น ใช้ฝั่ง Server |
| Public IP หรือโดเมนของ Cloud | ปลายทางที่ Client ใช้เชื่อมต่อผ่านอินเทอร์เน็ต |

`0.0.0.0` ไม่ใช่ Public IP ที่ให้ Client ใช้เป็นปลายทาง และการ bind ที่ค่านี้เพียงอย่างเดียวไม่ได้เปิด Firewall ให้โดยอัตโนมัติ

### ขั้นที่ 6: ทดสอบด้วยคอมพิวเตอร์จริงสองเครื่อง

| การทดสอบ | ผลที่คาดหวัง |
| --- | --- |
| Client ทั้งสองเครื่องเชื่อมต่อ Cloud | Server รับการเชื่อมต่อทั้งสองได้พร้อมกัน |
| Client 1 ส่งหา Client 2 | Client 2 ได้รับข้อความผ่าน Server |
| Client 2 ตอบกลับ | Client 1 ได้รับข้อความผ่าน Server |
| ส่งข้อความภาษาไทย | แสดงผลถูกต้อง |
| ส่งหลายข้อความติดกัน | แยกข้อความได้ถูกต้องและเรียงลำดับตามที่ส่งผ่านการเชื่อมต่อ |
| รับข้อความที่ถูกแบ่งมาหลายส่วน | รอจนข้อความครบแล้วจึงประมวลผล |
| ปิด Client คนหนึ่ง | Server ยังทำงานและ Client ที่เหลือยังเชื่อมต่ออยู่ |
| Client อยู่คนละเครือข่าย | ทั้งสองยังเชื่อมต่อ Cloud และสื่อสารกันได้ |

## 6. เนื้อหาที่ต้องอธิบายสำหรับ R1

| เรื่อง | สิ่งที่ต้องอธิบาย |
| --- | --- |
| Client–Server | Server เป็นศูนย์กลางรับการเชื่อมต่อและส่งต่อข้อความ |
| IPv4 | ใช้ระบุที่อยู่ของเครื่องปลายทาง |
| TCP | ใช้ขนส่งข้อมูลแบบมีการเชื่อมต่อ รักษาลำดับ และส่งข้อมูลซ้ำเมื่อสูญหายขณะที่การเชื่อมต่อยังทำงาน เหมาะกับข้อความแชต |
| Port | ระบุช่องทางของโปรแกรม Server บนเครื่อง เช่น `5000` |
| Socket | ช่องทางที่โปรแกรมใช้ส่งและรับข้อมูลผ่านเครือข่าย |
| กติกาข้อความของแอป | ใช้ JSON ระบุชนิดคำสั่งและข้อมูล พร้อมตัวจบบรรทัดแบ่งข้อความ |
| Thread | แยกงานรับข้อมูลเพื่อให้รองรับหลาย Client พร้อมกัน |
| Cloud | ให้ Client ติดต่อ Server ผ่านอินเทอร์เน็ต จึงไม่ต้องใช้ Wi-Fi เดียวกัน |

## 7. สไลด์และลำดับเดโมที่เสนอ

2. **Protocols:** ใช้อะไร ทำไมเลือก และใช้ตรงไหนในระบบ

4. **Demonstration:** เชื่อมต่อ Client สองเครื่อง ส่งข้อความทั้งสองทาง และแสดงการทำงานบน Cloud
